# B2 — Belt renders as one belt

Status: docs. Source: playtest feedback 8.

## What and why

A belt is `SIZE.m(0.25)` x `SIZE.m(0.1)` = 25 x 10 cells. Every one of those
cells draws a surface stripe, and every third column draws an arrow on every
row, so a placed belt reads as ten thin belts stacked on top of each other.
The player should see one belt: a surface with arrows on top, and a plain
body below it. The look must follow the belt size constant, so changing
`size.h` changes the belt without touching the drawing code.

The world model stays as it is: a belt is a row of belt cells, each with its
own direction in `beltCells`. No belt object, no stored "row index".

## Current behaviour

### Placement

- `regBuilding` for belt sets `size: { w: SIZE.m(0.25), h: SIZE.m(0.1) }`,
  `shapes: ['line']`, `vertical: false`
  (`js/PlayerInteract/Buildings/Belt.js:130-136`).
- `buildPlan` turns the drag into line cells, then `thickenCells(cells, size)`
  (`js/PlayerInteract/Build.js:76-85`). `thickenCells` adds `dx` in
  `0..w-1` and `dy` in `0..h-1` to every line cell (`js/sizes.js:10-27`).
  The drag line is the **top** row; the body hangs 9 rows **below** it, and
  the line is also widened 24 cells to the right. A click places a 25 x 10
  block; a drag of length L places (L + 25) x 10.
- `snapLine` allows horizontal and 45° lines (`js/lib/Shape.js:52-62`), so a
  belt can be a diagonal staircase of overlapping 25 x 10 blocks. Every cell
  gets the same code from `shapeHeading` (`js/lib/Shape.js:84-90`).
- `beltFits` (`Belt.js:19-26`): every cell must be in bounds and `OPEN`, and
  the cell above it must be in bounds and not `RIGID`. Lower rows check
  cells of the same plan, which are still open at check time, so they pass.
- `beltPlace` (`Belt.js:28-35`) writes `BELT_DECK` and the direction code for
  every cell, all ten rows alike.

### Movement

- `planBeltMoves` (`Belt.js:37-53`) plans one move per belt cell: from the
  cell directly above it `(x, y-1)` to `(x+dx, y-1+dy)`.
- `applyBeltMoves` (`Belt.js:55-70`) only moves `MOVABLE` material (powder,
  liquid; `js/materials.js:186`). Belt is `structure`
  (`js/materials.data.js:306-316`), so not movable.

Result: **only cells whose upper neighbour is not belt move cargo.** In an
intact belt that is the top row. Rows 2-10 each plan a move whose source is
a belt cell, which `applyBeltMoves` drops. They are inert, and cost 9 of 10
planned moves every tick.

A lower row becomes a working surface as soon as the cell above it stops
being belt (top row erased, see edge cases). Behaviour is already defined
per cell, by its upper neighbour.

### Drawing

- The belt body is drawn by the world bitmap from the material colour
  `[96, 88, 76]` with grain 5 (`js/render.js:82`, `js/materials.data.js:310`),
  like any material. This part is already one piece.
- `drawBelts` (`Belt.js:111-126`), shell code in a Mixed file, runs after the
  bitmap (`js/render.js:496-498`). For **every** entry in `beltCells` it
  fills a stripe `z * 0.3` tall at the top of the cell (`Belt.js:120-121`)
  and, when `x % ARROW_EVERY === 0`, draws a one-cell arrow
  (`Belt.js:122-124`, `drawFlowArrow` in `js/render.js:310-331`). Ten rows of
  stripes and arrows are the stacked look.
- It returns early when `view.zoom < 2` (`Belt.js:113`).
- The build preview does the same: arrows on every plan cell with
  `c.x % ARROW_EVERY === 0` (`js/PlayerInteract/Build.js:200-205`), so the
  ghost of a belt also looks like ten belts.

## Proposed behaviour

One rule for both drawing and movement:

```
surface cell  = belt cell whose upper neighbour is not BELT_DECK
body cell     = every other belt cell
```

This is a property of a single cell and its neighbour, so it needs no new
state and fits the world model. It is the rule `applyBeltMoves` already
obeys in practice, so the visuals show exactly the cells that move cargo.

Drawing:

- Body cells draw nothing extra. The material bitmap already fills them as
  one piece.
- Surface cells draw the stripe and the arrows. Stripe height and arrow size
  are derived from the belt's `size.h`, not from one cell, so a taller belt
  gets a thicker surface and larger arrows. Proposed: stripe height
  `max(1, z * h * 0.2)` drawn from the top of the surface cell down, arrow
  length about `h * 0.6` cells, centred in the body under the surface cell,
  spaced `ARROW_EVERY` derived from `h` (about one arrow per `h` columns)
  instead of the fixed 3. Exact ratios are tuned in the code step.
- Each arrow takes its direction from its own surface cell's code, so
  opposite belts side by side keep their own arrows.
- The build preview uses the same rule on the plan: arrows only on plan cells
  whose upper neighbour is not in the plan.

Optional core change (open question 2): `planBeltMoves` skips body cells, so
it plans 25 moves per segment instead of 250. Outcomes are identical; only
the planned list shrinks.

## Shell vs core

| Part | Layer | Change |
|---|---|---|
| `drawBelts` | shell code in Mixed `Belt.js` | surface rule, scaled stripe and arrows |
| `drawBuildPreview` | shell code in Mixed `Build.js` | arrows on top plan cells only |
| `ARROW_EVERY` | used by both | derived from belt `size.h`, or kept |
| `planBeltMoves` | core | none required; optional skip of body cells |
| `beltFits`, `beltPlace`, `beltCells` | core | none |

The required change is shell only. A shared core predicate
`beltSurface(i)` (`mat[i - W] !== BELT_DECK`) would let `planBeltMoves` and
`drawBelts` use one definition; it has a caller in core only if the optional
skip is taken.

## Edge cases

- **Belt partially erased.** Erase is a rect (`Build.js:79`), so any set of
  cells can go. Erasing the top rows of some columns exposes the next row:
  those cells become surface, draw the stripe, and already move cargo. A hole
  in the middle of the body makes the cell under the hole a surface; it moves
  cargo into and out of the hole, which matches what it draws. Erasing the
  bottom rows changes nothing visible on top.
- **Adjacent belts, side by side.** Each surface cell draws its own arrow, so
  a left-moving belt next to a right-moving one shows both directions at the
  seam. With `x % ARROW_EVERY` on world x the arrow grid is continuous across
  belts; a short belt (one segment, 25 wide) still gets arrows.
- **Adjacent belts, stacked.** A belt cannot be placed directly under
  another: the cell above its top row is belt, which is `RIGID`, so
  `beltFits` rejects it. With a gap of one open row both belts keep their own
  surface. The reverse is allowed: a belt placed so its bottom row rests on
  another belt's top row passes `beltFits`, and the lower belt's top row
  turns into body and stops moving cargo. The surface rule draws exactly
  that: one merged slab with one surface on top.
- **Diagonal belt.** The top surface is a staircase; the rule marks each step
  cell as surface. Arrows point along `(dx, dy)` as today.
- **Arrow size vs partial height.** If arrow size uses the constant `size.h`,
  a column eroded to fewer rows draws an arrow larger than its body, spilling
  below. Per-column depth would need a scan down the column each frame.
- **Zoom < 2.** `drawBelts` returns today, leaving only the bitmap body.
  With arrows scaled to `h` (10 cells), an arrow is 6 px at zoom 1 and
  could be drawn. Keep the early return, or move the cut-off to where the
  scaled arrow becomes unreadable (open question 4).
- **Stale entries.** `beltCells` drops cells that are no longer `BELT_DECK`
  only in `planBeltMoves`, which runs every `interval` frames. `drawBelts`
  may draw a surface on a just-destroyed cell for up to 2 frames. Existing
  behaviour; the surface rule should also check `mat[i] === BELT_DECK`.
- **World margin shift / chunk save.** `shiftBelts`, `beltsOutColumn`,
  `beltsIn` (`Belt.js:78-107`) keep per-cell codes; the surface rule reads
  `mat` only, so it needs nothing from them. At the top edge of the world
  (`y = 0`) the cell has no upper neighbour: treat it as surface for drawing;
  movement already skips it (`Belt.js:50`).

## Open questions

1. **Lower rows are inert.** Rows 2-10 never move cargo; they are a 9-row
   solid body that only becomes active when uncovered. Is that the intent
   (belt = a thick slab with a working top), or should the belt be one row
   of moving cells on a non-belt support (e.g. body cells of a separate
   inert material, or `size.h = 1`)? Visuals and behaviour agree once the
   surface rule is in, so this does not block B2, but it decides whether the
   body should look like a belt at all.
2. **Skip body cells in `planBeltMoves`?** Same outcomes, 10x fewer planned
   moves. It is a core change and needs its own unit test; in or out of B2?
3. **Arrow size source.** Constant `size.h` (simple, wrong on eroded columns)
   or per-column depth (correct, costs a scan)? Proposal: constant.
4. **Zoom cut-off.** Keep `z < 2` return, or draw scaled arrows down to
   zoom 1?
5. **Width thickening.** `size.w = 25` widens every drag by 24 cells to the
   right, so the belt starts at the cursor but ends 24 cells past it. Not
   part of B2, but the player may read it as a rendering bug; separate task?
6. **Preview.** Include the build preview (`Build.js:200-205`) in B2, or only
   placed belts?

## Decisions (approved 2026-10-18)

1. Keep the thick slab with one working top row.
2. Include the `planBeltMoves` change (skip body cells) with its own test.
3. Arrow size comes from the constant `size.h`.
4. Keep the zoom < 2 cut-off.
5. The 24-cell overhang past the cursor is task B3.
6. The build preview uses the same surface rule.
