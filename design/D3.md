# D3 — HUD text is not selectable

Status: docs. Feedback 15. Shell only: `style.css`.

## What and why

Dragging the mouse during play highlights HUD text in blue: panel labels,
prices, hotbar names, menu text. It looks broken and hides what it covers.
The game has nothing the player needs to copy, so text selection is switched
off for the whole page.

## Current behaviour

- No `user-select` rule exists anywhere in `style.css` or `index.html`.
- The canvas swallows only the context menu and the wheel
  (`js/input.js:156-170`); `mousedown` is not prevented, so a drag that
  starts on the canvas (building a wall, drawing a belt) extends a selection
  into HUD panels on top of it.
- Double-click selects a word in any panel; Ctrl+A selects the whole HUD.
- Form controls in the page (`index.html`):
  - `#set-mute` checkbox (`:166`), `#set-volume` and `#set-grab` range
    sliders (`:170`, `:179`);
  - key rebinding uses buttons plus a capturing `keydown` listener
    (`js/settings.js:330-341`, `:476`), not a text field.

  There are no text inputs, textareas or `contenteditable` elements.

## Proposed behaviour

One rule on `body` (`style.css:29-37`):

```
user-select: none;
-webkit-user-select: none;
```

`body` rather than `#hud`, so that a drag from the canvas cannot start a
selection either. The prefixed form covers WebKit when the launcher falls
back to a default browser that is Safari (`main.go:211`).

Checkbox and range inputs keep working: they do not depend on text
selection. Rebinding keys reads `keydown` and is not affected.

No rule re-enables selection for text fields, because there are none; a rule
for elements that do not exist is dead code. When the first text field is
added, it gets `user-select: text` in the same change.

## Affected files

| File | Change |
|---|---|
| `style.css` | two declarations on `body` |

## Edge cases

- **Future text input.** Under an ancestor with `user-select:none`, WebKit
  has shipped bugs where typed text cannot be selected or the caret is not
  placed. The future field needs its own `user-select:text`.
- **Cursor.** `user-select` does not change the cursor; panels still show the
  I-beam over text.
- **Drag of an existing selection** is impossible once nothing can be
  selected, so no `dragstart` handling is needed.

## Open questions

1. Should any text stay copyable — the help steps, the boot terminal log,
   Mission Control messages? Proposed: none.
2. Show the default arrow instead of the I-beam over HUD text
   (`cursor: default` on `#hud`)? Not requested; separate from selection.

## Decisions (approved 2026-10-18)

1. No text stays copyable.
2. HUD uses `cursor:default`.
