# E1 — Sorter

Status: docs. Feedback 17. Next steps (model, tests, code) wait for approval.

## What and why

Today a belt line carries whatever lands on it, so the pickup zone fills with
soil and slag next to the ore. The sorter is a belt piece with one chosen
material and a mode:

- `pass`: only that material goes on along the belt; everything else drops.
- `block`: that material drops; everything else goes on.

"Drops" means the cargo falls out the bottom of the sorter, so a second belt or
a pile underneath catches what was sorted out.

## How belts work today

- Material: `belt` is a `structure` with `grips` (`materials.data.js:307`), so
  it is `RIGID` and `FIXED` (`materials.js:187`, `:191`).
- Per-cell data: `beltCells`, a `Map` from cell index to a direction code
  0..8 (`Belt.js:3`, `beltCode`/`beltDx`/`beltDy` at `Belt.js:7-17`).
- Footprint: a belt drag is a `line`, and every point of it is thickened to
  `size = { w: SIZE.m(0.25), h: SIZE.m(0.1) }` = 25 x 10 cells, anchored at the
  top-left (`Build.js:76-85`, `sizes.js:10-27`, `Belt.js:130`). A belt is 10
  rows thick; all cells of one drag share one code (`Belt.js:28-35`).
- Fit: every cell `OPEN`, and the cell above every cell not `RIGID`
  (`Belt.js:19-26`).
- Motion: every `pieceStats('belt').interval` frames (3/2/1 by level,
  `Belt.js:72-76`, `:134`) each belt cell plans a move of the cell above it to
  the cell above-and-onward (`Belt.js:37-53`). Only the top row really moves
  anything: for inner rows the cell above is belt, which is not `MOVABLE`.
  `applyBeltMoves` moves `MOVABLE` cargo (powder, liquid, `materials.js:186`)
  into an `OPEN` target, carries temperature, swaps with gas, and uses
  `beltArrived` so one cell moves once per tick (`Belt.js:55-70`).
  Stale entries (cell no longer belt) are dropped in the plan pass
  (`Belt.js:40-43`).
- Removal: `owns`/`remove` hooks (`Belt.js:143-146`), called by `eraseCells`
  through `ownerAt` (`Build.js:102-126`).
- Window shifts: `shiftWindow` calls `shiftBelts(dx)` (`world.js:770`,
  `Belt.js:78-85`). Columns leaving the window take their entries out with
  `beltsOutColumn` into `chunk.belts` (`world.js:665-680`, `Belt.js:87-100`);
  entering columns put them back with `beltsIn` (`world.js:682-695`,
  `Belt.js:102-107`). The chunk store carries the value as an opaque number.

## Proposed behaviour

### Model: a sorter cell is a belt cell with a filter

One new material `sorter` (`structure`, `grips`, own colour). Its per-cell data
lives in the same `beltCells` map, packed into the same number:

```
value = code | mode << 4 | target << 8
  code    0..8   direction, as today
  mode    0 belt (no filter), 1 pass, 2 block
  target  material id 0..255 (mat is a Uint8Array)
```

Invariant: `mat[i] === BELT_DECK` ⇔ entry with `mode 0`;
`mat[i] === SORTER` ⇔ entry with `mode 1|2`. Existing belt values are already
valid (`mode 0`, `target 0`), so nothing stored today changes meaning.

Why the shared map: `world.js` already shifts, saves and restores `beltCells`
values verbatim. A packed number rides through `shiftBelts`, `beltsOutColumn`,
`chunk.belts` and `beltsIn` with no change to `world.js` and no second copy of
those three functions. A separate `sorterCells` map would need exactly that
copy (rejected). `beltDx`/`beltDy` must read `code & 15`.

### Motion

The sorter runs inside `tickBelts`, at the belt interval (belt level speeds it
up too). For each entry whose cell above holds `MOVABLE` cargo `m`:

- accepted (`pass` and `m === target`, or `block` and `m !== target`, or
  `mode 0`): the plain belt move, unchanged;
- rejected: the cargo goes down the **chute** — from the cell above the sorter
  straight to the first non-sorter cell below the sorter column. It moves only
  if that cell is `OPEN`, carrying temperature like a belt move and marked in
  `beltArrived`.

Accept or reject is decided at apply time on the cargo that is actually there,
not at plan time, because earlier moves in the same tick change cells.

Failure outcome: chute landing not `OPEN` (pile reached the bottom, rock, belt)
→ the rejected cell stays on top of the sorter. It blocks the cell, and cargo
behind it queues. No notice (D1); the jam is visible.

Inner sorter rows do nothing, as inner belt rows do: the cell above them is
not `MOVABLE`.

### Footprint and placement

- `size = { w: SIZE.m(0.1), h: <belt h> }` = 10 x 10 cells, shape `line`. The
  height must equal the belt height, otherwise belt rows stay under the sorter
  and every chute lands on belt and jams. Both read one constant.
- Fit: each cell is `OPEN`, `belt` or `sorter`; the cell above each cell is
  not `RIGID` unless it is part of the plan or itself belt/sorter.
- Place: over a belt or sorter cell the cell keeps its own `code` and gets the
  new `mode`/`target`; over an open cell it takes the drag heading. So
  dropping a sorter onto an existing line needs no direction from the player,
  and re-placing over a sorter is how it is reconfigured — no edit mode.
- Erase: right-drag as for belts; `owns` is `mat === SORTER`, `remove` deletes
  the entry. Erasing returns open cells, as for belts.

### UI (mouse first, D6)

While the sorter tool is selected a pick bar shows under the hotbar, next to
the shape bar (`index.html:71`, `hud.js:157-178`, clicks through `onBarClick`,
`input.js:174`):

- two buttons: `pass` / `block`;
- one swatch per selectable material: colour plus `matLabel(id)`
  (`materials.js:48`), so names come from the existing `mat.*` keys.

The choice is tool state like `buildShape`: `sortMode`, `sortTarget` in the
sorter file, changed only through a setter called by the shell. Defaults:
`pass`, first selectable material. The preview tint stays ok/bad; the preview
top row is drawn in the target material's colour. No hotkey is required; if
one is added later it duplicates a bar button.

Drawing: top row stripe in the target colour, a mode glyph every
`ARROW_EVERY` cells (arrow for `pass`, crossed arrow for `block`), and a dark
chute column. Follows B2 once it lands (top row only).

### What "a material" is

Selectable set: every material with `MOVABLE[id]` — exactly what a belt can
carry: soil, sand, gravel, coal, ferrite, slag, water, lava, molten iron,
molten glass, ember, cullet, iron scrap.

Cell id, not cargo group (`CARGO`, `materials.js:163`; `GOODS`,
`market.js:1-8`). Among movable materials each cargo group is a single id
(`glass` and `iron` are solid and never ride a belt; only `cullet` and
`iron_scrap` do), so cell id loses nothing for goods and also sorts soil and
slag, which have no group and are the main waste to get rid of.

## Edge cases

- No belt after the sorter: accepted cargo falls off the end, as at a belt end.
- Diagonal line: forward move uses the cell's own `code`, so a sorter on a
  slope climbs/descends like a belt; the chute is always straight down.
- Partly erased column: chute stops at the first non-sorter cell and drops
  there if it is `OPEN`.
- Sorter clicked half off the belt: the preview shows the 10 x 10 block; cells
  in rock fail the fit (red). Cells that end up above the belt top form a step
  that blocks cargo — see open question 2.
- Liquids: a liquid selected in `pass` drops the solids; liquid that spreads
  sideways on its own is not the sorter's business.
- Hot cargo keeps its temperature through the chute.
- Chunk edge: entries are per cell; a sorter split across two chunks saves and
  loads per chunk like a belt.
- Stale entry (cell turned into something else): dropped in the plan pass as
  today, for both materials.
- `target` is a material id; the material table order is fixed per build, so
  ids stay valid while the game runs. Saving to disk (Storage, step 5 of
  `SIMULATION.md`) must store names or a table version.

## Tests the model step will state

- Pass/block: a mixed column on a sorter splits as specified per tick.
- Chute: rejected cargo lands below the sorter; blocked landing jams.
- Placement over belt keeps codes; over sorter rewrites filter only.
- Invariant: material ⇔ entry ⇔ mode, after `simulate()`, after erase.
- Shift out and back (`shiftWindow` both ways) preserves every packed value.

## Open questions

1. Chute or plain drop: is a 10-cell move straight through the sorter
   acceptable, or should the sorter be a one-row grate with open space below
   (cargo drops one cell and falls by physics, but the line needs a gap)?
2. Snap: should placement snap the sorter's top row to the belt top row under
   the cursor, or is the free 10 x 10 block with a red/green preview enough?
3. Sorter width 10 cells (0.1 m) — fine, or one belt segment (25)?
4. Selectable set: all 13 movable materials, or only those the player has
   seen/mined so far (shorter bar)?
5. Pick from world: also allow clicking a cell with the sorter tool held to
   take its material (an eyedropper), or bar only?
6. Unlock price 480 and no levels — OK?

## Decisions (approved 2026-10-18)

1. The 10-cell chute through the sorter is accepted.
2. Placement snaps the sorter's top row to the belt's top row.
3. Width 10 cells.
4. The bar offers all 13 belt-riding materials.
5. No eyedropper for now.
6. Unlock price 480, no levels.
