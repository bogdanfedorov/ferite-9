# D2 — Interface scale

Status: docs. Feedback 6. Shell only: no core file changes.

## What and why

Playtest feedback: HUD text is too small (or too large) for some screens. The
player gets one slider in Settings that scales the whole HUD. The world canvas
does not change. The value is saved with the other settings and is applied on
the next start.

## Current behaviour

- The HUD is DOM, not canvas. `#hud` (`index.html:16-211`) is a fixed overlay
  over `<canvas id="game">` (`index.html:14`) with `pointer-events:none`;
  panels and buttons switch it back on (`style.css:48-57`, `style.css:61-69`).
- Every size is a hard px value in `style.css`: `body{font-size:14px}`
  (`style.css:34`), about 120 `font-size` declarations from 9px to 54px, px
  paddings and widths, the `#hud` grid `200px 200px 1fr 200px 200px`
  (`style.css:53`), hotbar width `min(620px, calc(100vw - 28px))`
  (`style.css:436`). There is no shared unit to multiply.
- Breakpoints shrink the HUD by viewport size (`style.css:700-742`).
- The menus (`#inventory`, `#boot`, `#intro`, `#pause`, `#help`,
  `#settings`) are children of `#hud` (`index.html:75-209`), so anything that
  scales `#hud` scales them too.
- The probe chip is the only HUD element placed by script. `placeProbe`
  (`js/hud.js:118-127`) sets `left`/`top` to `input.mouse.x/y`, which are
  viewport px taken from the canvas rect (`js/input.js:115-121`), and flips
  against `window.innerWidth/innerHeight` using `offsetWidth/offsetHeight`.
- The only canvas text is the room bin labels in `drawRoomBins`
  (`js/render.js:452-490`). They are world objects and follow world zoom.
- Settings: one `settings` object (`js/settings.js:100-106`) saved whole as
  JSON under `ferit9.settings` (`js/settings.js:202-209`). `loadSettings`
  clamps each field and falls back to a default for a missing or bad value
  (`js/settings.js:161-200`). Sliders follow the volume/grab pattern:
  `input` updates the value label, `change` saves and calls the settings hook
  (`js/settings.js:452-466`). `applyVision` already writes CSS variables on
  `document.documentElement` (`js/settings.js:276-283`).
- Launchers: the Go launcher opens Chrome/Edge/Chromium with `--app`, else the
  default browser (`main.go:147-213`); Electron is Chromium. Browser zoom
  (Ctrl +/-) exists but scales the canvas too and changes `innerWidth`.

## Ways to scale

| Way | Effect | Verdict |
|---|---|---|
| CSS variable multiplied into every px value | Touches ~200 declarations; easy to miss one; media queries cannot use it | Too much churn for one feature |
| Convert px to `rem`, scale `html{font-size}` | Same churn; also scales the settings screen text outside `#hud` in future | Same |
| `transform: scale()` on `#hud` | No reflow: the overlay grows past the window unless sized `100%/s`; `position:fixed` children (probe, screens) become relative to the transformed box | Rejected |
| `zoom` on `#hud` | One declaration. Layout reflows inside the zoomed box, so the grid, wrapping and `1fr` columns adapt. Hit testing of DOM buttons stays correct (the browser maps events). Chromium, Safari, Firefox 126+ | **Proposed** |

## Proposed behaviour

Data:

```
settings.uiScale   integer percent, UI_SCALE_MIN..UI_SCALE_MAX, default 100
UI_SCALE_MIN = 75, UI_SCALE_MAX = 150, step 5     (js/settings.js constants)
```

Old saves have no `uiScale`; `loadSettings` gives 100 through
`clampInt(saved.uiScale, UI_SCALE_MIN, UI_SCALE_MAX, 100)`.

Applying: `applyUiScale()` in `js/settings.js` sets `--ui-scale` on
`document.documentElement` to `uiScale / 100`, next to `applyVision`.
`style.css` gets `#hud{zoom:var(--ui-scale,1)}`. Called once in
`initSettings` after `loadSettings`, and when the slider is released.

Slider: a new row in the Settings screen, same markup as volume/grab
(`index.html:168-172`): `<input type="range" id="set-ui-scale">` with a value
label `set-ui-scale-val` showing `{n}%`. On `input` only the label updates;
on `change` the value is applied and saved. Applying while dragging would
resize the settings card under the cursor and move the thumb away from it.

Probe chip: `placeProbe` divides the mouse position and the window size by
the scale before it places and flips the chip, so the chip stays at the
cursor. All values in one function are in the zoomed coordinate space.

Canvas: untouched. It is a sibling of `#hud`, so `trackMouse`, `screenToWorld`
and world zoom see the same px as now.

Text: new keys in `js/lang/en.js`, `uk.js`, `pl.js`:
`set.ui` (group heading), `set.uiScale` (row label). The `%` value needs no
translation. `wiki/Settings.md` gets a short section.

| File | Change |
|---|---|
| `js/settings.js` | `uiScale` field, constants, load clamp, `applyUiScale`, slider binding, panel refresh |
| `style.css` | `#hud{zoom:var(--ui-scale,1)}` |

## Edge cases

- **Large scale on a small window.** Breakpoints test the real viewport, not
  the zoomed layout width (`innerWidth / s`). At 150% in the 1280×800 launcher
  window the HUD lays out as if the window were 853 px wide but gets the
  1280 px rules, so side panels and the hotbar may overlap. `vw` inside a
  zoomed element also scales, so `calc(100vw - 28px)` on the hotbar can
  overflow. Needs a browser check at 150% on 1280×800 and 1024×600.
- **Probe flip.** `offsetWidth` under `zoom` must be checked in Chromium; the
  flip compares it with the divided window size.
- **Menus scale too.** Settings, help and the inventory grow with the HUD; at
  150% on a short window the cards rely on their existing scroll
  (`style.css:548-550`).
- **Bad stored value** (string, NaN, out of range): clamped or default 100,
  same as volume.
- **Storage blocked**: the setting works for the session, as the others do
  (`settingsStored`).
- **Browser zoom** stacks with this setting; nothing to handle.

## Open questions

1. Range and step: 75–150% in 5% steps, default 100?
2. Do menus (settings, help, inventory, intro, boot terminal) scale, or only
   the in-game corners and hotbar? Scaling `#hud` covers both; excluding the
   menus means moving them out of `#hud` or zooming only selected children.
3. Should the world labels drawn on canvas (room bins) follow the UI scale?
   Proposed: no, they are world objects.
4. Large scale vs breakpoints: accept overlap at the top of the range, cap the
   scale by window size, or rewrite breakpoints as container-size rules?
5. Tests: `settings.js` is shell and is not loaded by `test/core.js`. Is the
   load clamp tested by a small test that loads `settings.js` with a fake
   storage, or is this feature checked in the browser only?

## Decisions (approved 2026-10-18)

1. Range 75–150% in steps of 5, default 100; the top is capped by window size.
2. Menus scale too.
3. Test-room bin labels do not scale.
4. Checked in the browser only (shell).
