# D6 — Every action reachable by mouse

Status: docs. Feedback 18. Nothing below is built yet.

## What and why

A player who does not know a key never finds what it does. The heat map is
toggled by `T` and nothing on screen shows it exists.

**The rule.** Every action a player can trigger has a visible control that
works with the mouse. Keys stay as shortcuts. Every control shows its key on
hover, so the mouse path is also how a player learns the key.

Only movement is exempt (`up` `down` `left` `right`, jetpack on `up`).
Moving the module is the keyboard's job, and click-to-move is another
feature, not a missing button.

## Proposed UI

Three additions and one shape.

**1. System row on the module plate**, where the old buttons were. It holds
menu (pause), help, settings and sound. Sound shows its state (on/off).

**2. View switcher** directly under the module plate, above the heat legend
the heat view already shows. It is a row of overlay buttons in the ONI style:
one button per view, at most one view on, clicking the active view turns it
off. Today it has one button, `heat`. A later view (power, ownership, D5's
pickup view if it becomes an overlay) adds one button and nothing else.

**3. Tool menu button** at the right end of the hotbar, and a close button in
the tool menu card.

**4. `square` becomes a shape** in `SHAPES`, next to `rect`, listed in the
`shapes` of Wall and Pad. It appears in the shape bar like any other shape, so
`R` and the mouse both reach it. `buildEven` and the read of `input.keys.shift`
in `Build.js` go away, and the core no longer reads the keyboard. Holding
`Shift` stays as a shortcut: while held it turns `rect` into `square` for the
current drag.

### One dispatch path

A button and a key run the same function. Each new control carries
`data-act="<KEY_ACTIONS id>"`; one click handler calls `KEY_ACTIONS[act]`,
the same way `onKeyDown` does. `pause` joins `KEY_ACTIONS` so `Esc` and the
menu button share it. No action gets a second implementation.

### Tooltips

A control with `data-act` gets its hover text from data already there: the
name is `set.key.<act>` (the label the key list in Settings already uses), and
the key is `bindText(act)`. `refreshKeyLabels` already walks every
`[data-bind]` on rebind and language change; it also writes the tooltip, so a
rebound key shows up on hover right away. Hotbar cells, the drone button and
the shape bar get the same treatment (`slotN`, `drone`, `shape`).

### State and notices

Heat and sound buttons show their state, lit or not. The notices they send
today (`msg.heatOn/Off`, `msg.soundOn/Off`, `msg.buildShape`) then only echo
what the player just did, which D1 removes. D6 leaves them; D1 decides.

## i18n keys

Reused: `set.key.<act>` for every tooltip name, `set.key.inventory` for the
tool menu button, `ui.help` and `ui.settings` for the system row labels.

New, in all three languages:

| Key | en |
|---|---|
| `ui.tip` | `{name} · {key}` |
| `ui.views` | `view` |
| `ui.close` | `close` |

`set.key.pause` is only a tooltip name; `Esc` stays reserved and does not
appear in the rebinding list.

## Open questions

1. Tooltip: native `title` (no code, slow to appear, unstyled) or one shared
   HUD tooltip element styled like the probe chip?
2. Shift: keep it as a hold-shortcut for `square`, or drop it once `square`
   is a shape and `R` reaches it?
3. View switcher place: under the module plate (next to the legend it opens),
   or bottom right, which is empty today?
4. Should the system row include zoom `+` / `−`? The wheel is a mouse path,
   but a trackpad player may not find it.
5. D4 redesigns the tool menu. Is the hotbar tool button and the menu's close
   button done here, or moved into D4?
6. Movement exempt from the rule — agreed?

## Decisions (approved 2026-10-18)

1. One shared styled tooltip element.
2. Shift stays a shortcut for `square`.
3. The view switcher goes bottom right.
4. Add zoom +/− buttons.
5. The tool menu open and close buttons move to D4.
6. Movement (WASD, jetpack) is the one exception.
